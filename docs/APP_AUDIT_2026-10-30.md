# مراجعة تطبيق جاهز Live — 30 أكتوبر 2026

## ما تغيّر
- اختبارات اختيار من متعدد (حتى 30 سؤالًا، 2–6 خيارات في API و4 في المحرر، درجات موزونة) مع حساب الدرجة على الخادم، حفظ الإجابات، إشعار الطالب وولي الأمر، وإمكانية مراجعة المدرس. مفتاح الإجابة لا يدخل DTO الطالب أو ولي الأمر. الواجبات الكتابية تظل يدوية.
- منع تعديل الواجب المصحح عند طلبات متزامنة؛ تحقق ملكية المرفقات، وصلاحية حجز الطالب عند عرض ولي الأمر، وصحة درجات الأسئلة والمجموع.
- المحرر يحسب المجموع تلقائيًا؛ واجهة الطالب تعرض تقدم الإجابة وتوضح أن التسليم نهائي؛ وسوم للتصحيح الآلي والمراجعة والتسليم المتأخر.
- منع تضخيم الحضور بطلبات سريعة؛ حساب الوقت الفعلي مع حد أقصى لكل نبضة؛ تحقق من توافر البث أو التسجيل.
- تسلسل حجز آخر مقعد تحت قفل الحصة؛ معالجة وصول تأكيد دفع لحصة ملغاة، وتسلسل الاسترداد المتكرر؛ قفل حساب المدرس حتى عند أول طلب سحب.
- لا تمنح صلاحية المدير عند التسجيل العام لمجرد كتابة بريد موجود في ADMIN_EMAILS. حسابات الإدارة الحالية محفوظة؛ إنشاء المديرين عملية تشغيلية منفصلة.
- فشل رمز ربط ولي الأمر الخاطئ يعيد خطأ ويلغي إنشاء الحساب؛ تحقق توقيع الملفات ونوعها وأسمائها، ورسائل أفضل لحجم الملف والجلسة المنتهية.
- حالات إعادة المحاولة بدل الشاشة الفارغة أو انهيار المحفظة/الإدارة؛ فشل تحميل الجلسة لا يعامل كخروج؛ تحديث حالة قراءة التنبيهات محليًا.
- التحقق من الموعد الفارغ قبل تحويل التاريخ؛ مهلة لاتصال API والدفع؛ شاشة انتظار الدفع تعرض تحديث الحالة والعودة للحصص؛ عدم الادعاء بأن المبلغ لم يُخصم دون تأكيد.
- منع تخزين استجابات API وHTML القديم؛ تحميل صفحات الأدوار عند فتحها. ملف الدخول الرئيسي نحو 501 KB مقابل 631 KB قبل المراجعة (غير مضغوط؛ لا يمثل زمن الشبكة).

## التحقق
- TypeScript للـ core وDB والتطبيق والخادم: نجح.
- بناء التطبيق وAPI: نجح. تحذير حجم LiveKit والحزمة الرئيسية ما زال موجودًا.
- 54 تحققًا عبر API في قاعدة PGlite محلية منفصلة وبوابة mock وصندوق بريد محلي: جميعها نجحت. تشمل الرحلة الأساسية، صلاحيات الواجب، عدم تسريب المفتاح، مجموع الدرجات، إعادة التصحيح، التسليم المتزامن، آخر مقعد، الدفع المتأخر بعد الإلغاء، الملفات، ورمز ولي الأمر.
- نجحت نفس الاختبارات على PostgreSQL 17 داخل شبكة Docker داخلية معزولة وقاعدة مؤقتة بلا منافذ منشورة، ثم حُذفت حاويات الاختبار والشبكة.
- من المتصفح: إنشاء اختبار من حساب المدرس، تسجيل الطالب، اختياره وتسليمه وظهور 5/5؛ مقاس 390 بكسل دون تجاوز أفقي.
- سكربتات smoke/seed ترفض عنوان API غير محلي؛ اختبار VPS يعمل داخل حاويات معزولة وعنوان localhost، بلا بيانات أو أسرار الإنتاج. اختبار EasyKash يستعمل بوابة وهمية محلية فقط.

## حدود التحقق
لم تنفذ خصومات بنكية حقيقية أو إرسال SMTP إلى عملاء. اختُبر نقل فيديو اصطناعي حقيقي عبر LiveKit من الخادم إلى متصفح خارجي، دون استخدام كاميرا أو ميكروفون المستخدم. لم يُنفذ اختبار حمل لـ100 طالب أو اختبار صوت الميكروفون. احتفظت البيانات القديمة بدرجاتها وتصحيحها اليدوي.

## البث التجريبي دون اشتراك جديد
- LiveKit مستضاف على الخادم الحالي: حصة واحدة في الوقت نفسه، 25 طالبًا بالإضافة إلى المدرس، بلا تسجيل. حد أقصى 1 CPU و768MB للخدمة، وإعدادات فيديو اقتصادية.
- إنشاء الغرف وصلاحيات النشر يديرهما الخادم؛ الطلاب مشتركون بالمشاهدة. منع إنشاء غرف إضافية متزامنة بقفل قاعدة بيانات، ورفض سعة حصة أعلى من حد التجربة.
- API الداخلي غير منشور للعامة؛ الإشارة عبر HTTPS والوسائط عبر المنافذ المحددة. استثناء /rtc من سجل الوصول يمنع تدوين رمز الاتصال في URL.
- لا يوجد TURN/TLS على 443 في هذه التجربة؛ لا تُضمن الشبكات شديدة التقييد أو سعة 100 طالب. يلزم اختبار حمل قبل توسيع الحد. الملفات التشغيلية في infra/live-media.

## EasyKash على حساب التاجر الحالي
- مرجع Live منفصل glive_<UUID>، ومرجع Agent يحتفظ بمساره. توقيع SHA-512 موثق، تحقق من المبلغ بالقروش، واستعلام خادمي مستقل؛ معاملات المتصفح لا تؤكد الدفع.
- جسر محدود في callback الخاص بـAgent يمرر مراجع Live فقط إلى متحقق Live. أضيف توافق توقيع المزود الحالي مع الحفاظ على التوقيع السابق لفواتير Agent القديمة. التعديل محفوظ في infra/payments/agent-callback-bridge.patch.
- لا تُنشأ عملية مدفوعة دون رقم هاتف صالح. فشل إنشاء checkout يلغي حجز المقعد المؤقت. كود فوري/أمان لا يظهر إلا إذا أعاده استعلام موثوق.
- نقص المبلغ، الدفع المكرر، والاسترداد اليدوي تُعرض في قائمة مراجعة الإدارة. لا توصف العملية أو الحجز بأن المبلغ رُدّ قبل تأكيد المزود. رد الدفعة المكررة لا يلغي المقعد الأصلي؛ عكس مستحقات سبق صرفها لا يتكرر.
- لا يُخترع endpoint للاسترداد: ينفذه المشغّل من لوحة التاجر ثم يؤكده المزود. اسم التاجر الظاهر يتبع ملف EasyKash المعتمد؛ productName ليس تغييرًا للاسم البنكي.
